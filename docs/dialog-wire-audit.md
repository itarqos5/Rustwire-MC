# Dialog and custom-click wire audit

`packet::dialog` adds bounded, state-explicit `ClearDialog`, `ShowDialog` and
`CustomClickAction` body codecs and packet builders for protocols 771–776.
`DecodedPacket::Dialog` intercepts the two clientbound names before play-only
dispatch. Every public read/decode/write/encode/packet helper takes the state;
configuration bodies are never parsed using a play-state default.

## Exact state and representation boundary

| Packet | Configuration | Play | Direction |
|---|---|---|---|
| `clear_dialog` | empty body | empty body | clientbound |
| `show_dialog` | direct anonymous NBT | VarInt registry holder: zero then inline anonymous NBT, otherwise registry ID + 1 | clientbound |
| `custom_click_action` | identifier then length-framed optional anonymous NBT | same | serverbound |

All six state/direction combinations start at protocol 771. The audit checks
presence at 771–776 and absence at 763–770 against every exact hash-pinned
schema. Helpers reject other states and older versions. Custom clicks do not
enter clientbound typed dispatch.

`ShowDialog` reuses `RegistryHolder<Nbt>`. Inline values can be encoded in either
state with that state's distinct framing; registry references are forbidden in
configuration. References retain nonnegative, unshifted IDs and remain
unresolved. The largest accepted reference is `i32::MAX - 1`, whose shifted marker
fits a positive VarInt. Negative markers are malformed under Rustwire's existing
holder convention.

Dialog NBT is a required root. It is fully retained but not interpreted as a
dialog schema; an unknown dialog `type` string remains opaque data. Any supported
NBT root is representable, without claiming that a receiving dialog interpreter
accepts its meaning. Missing roots/TAG_End and unknown NBT tag IDs are errors.

## Corrected custom-click framing

Every pinned 771–776 schema describes the payload as a boolean `option` around
anonymous NBT. That shape is stale. The implemented wire body is:

1. A Minecraft resource identifier encoded as a protocol string
2. A VarInt byte length, at most 65,536
3. Exactly that many bytes containing one anonymous NBT root; a single TAG_End
   byte (`00`) means no payload

There is no boolean prefix. An absent payload therefore has length byte `01`
followed by root byte `00`. A zero-length sub-buffer is invalid. Scalar roots,
including a byte root beginning with `01`, must not be mistaken for an option
flag. The Rust API represents absence as `None` and a complete root as
`Some(Nbt)`.

The existing protocol-776 serverbound catalog correction also applies: play
custom-click is **0x44**, while the raw pinned schema says 0x43 because it omitted
the UUID spectator packet earlier in the sequence. The verifier explicitly
checks the stale input before applying this already established correction.
See [catalog provenance](../PROVENANCE.md#protocol-776-serverbound-catalog-correction).
No generated catalog is changed by this increment.

Read-only `javap` inspection of the previously acquired, SHA-256-verified official
26.2 inner server JAR establishes:

- Configuration binds the show packet's context-free codec; play binds its
  registry-aware codec. The dialog codecs are direct NBT versus registry holder
- Both states bind the same custom-click codec: identifier plus
  `optionalTagCodec` wrapped in `lengthPrefixed(65536)`
- `optionalTagCodec` uses nullable-tag reads/writes. `FriendlyByteBuf` encodes
  null as TAG_End and maps a root tag ID of zero back to null
- The custom-click NBT accounter has an allocation quota of 32,768 and a maximum
  of 16 container pushes

`tools/verify_dialog_bindings.py` reproduces the JAR and eleven class-hash checks
and the selected static binding checks using an existing JDK. It invokes only
`javap`, never game classes, and neither downloads artifacts nor saves their
implementation text. This is static evidence, not an executed serializer oracle.
The independently pinned schemas remain unchanged and visibly disagree where
noted; they are not silently rewritten to match the Rust codec.

## Budgets, strictness and non-goals

All three codecs check the body-byte budget, fully consume decoded bodies, and
leave caller readers/writers unchanged on failure. Direct and holder-inline NBT
reuse the shared bounded NBT implementation. NBT nodes, collection lengths,
strings and recursive depth obey caller limits; the identifier and payload
also share the complete packet-byte budget.

Custom-click payload framing additionally enforces the exact 65,536-byte cap.
Length is checked before reading the sub-buffer. The decoder requires one whole
NBT root and no unused bytes inside it; trailing data outside the sub-buffer is
also rejected. The official length wrapper itself can skip unused inner bytes;
Rustwire's exact inner completion is an intentionally stricter codec policy.

For custom-click NBT, Rustwire also imposes a **conservative depth cap of 15**
under its root-at-zero tag-recursion convention, further lowered by the caller.
That allows at most sixteen root-inclusive tag levels, hence at most sixteen
nested containers. It can reject structures whose deepest scalar would still
fit the receiving JVM's container-only accounting. It is not described as an
exact match to `NbtAccounter.maxDepth(16)`.

The JVM's **32,768 allocation-accounting quota is not reproduced** by Rustwire's
node, collection and byte budgets. An envelope accepted by this codec can still
be rejected by a server's allocation quota or semantic action validation. In
particular, the exact 65,536-byte synthetic fixture establishes the framing cap,
not receiving-server acceptance. No release-specific JVM allocation size is
invented or equated to Rust heap usage.

Identifiers reuse the existing version-aware validator and preserve spellings
and aliases rather than normalizing them. A URL-shaped valid identifier remains
data. No codec renders dialogs, resolves registry IDs, executes click actions,
opens URLs, contacts services, sends automatic replies or changes caller trust
or consent policies. Existing unsupported unframed-item fallback still retains
the entire original `RawPacket`; malformed selected dialog bodies remain errors.

## Validation and reproduction

The independent Python encoder supplies **102 fixtures** across 36 supported
packet/state/direction combinations. Tests exercise all **588 strict prefixes**,
trailing bytes, exact/undersized byte budgets, transactional stream operations,
all version/state/direction gates, malformed NBT and holder markers, absent and
scalar click roots, zero-length and oversized inner frames, string/collection/
aggregate-node limits, conservative depth boundaries and exact 65,536-byte
framing. Two in-memory connection tests establish correct configuration/play
dispatch without automatic writes and unchanged unsupported-payload fallback.

Ten Python regression controls build tiny synthetic schemas from committed
fixture facts. They pass in a clean copy without `research/protocols`, downloads
or network access. The actual hash-pinned schema check remains a separate gate.

```sh
python3 tools/verify_dialog_schemas.py
python3 -m unittest discover -s tools -p 'test_verify_dialog_schemas.py' -v
cargo test --locked --offline --no-default-features --test dialog --test dialog_connection
cargo test --locked --offline --all-features --test dialog --test dialog_connection \
  --test typed --test common --test server_metadata --test server_metadata_connection
cargo clippy --locked --offline --all-features --lib --test dialog --test dialog_connection -- -D warnings
RUSTDOCFLAGS='-D warnings' cargo doc --locked --offline --all-features --no-deps
cargo fmt --all -- --check
# Optional static gate, only with an existing official 26.2 inner JAR and JDK:
python3 tools/verify_dialog_bindings.py --jar /path/to/server-26.2.jar
```

No game/server process, upstream serializer or live network session was run.
Official artifacts, mappings and disassembly are not distributed. Focused Rust
checks use the existing stable toolchain; integrated suites and exact-commit
Rust 1.88 CI are separate gates.

Full-suite check on the frozen 243786cd baseline plus this increment: **525
no-default-feature tests and 564 all-feature tests passed**, with zero failures
or ignored tests. These are Rust library tests, not executed official serializers
or receiving-server validation; later integrated changes need their own gates.
